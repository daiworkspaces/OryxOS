# OryxOS：企业 Agent 操作系统（Agent Harness OS）

## 定位

OryxOS 是面向企业私有部署的 Agent 操作系统。它的北极星体验是：

> 用一句自然语言发布任务 → 底座拆解任务 → 组织一支 Agent 团队 → 多个 Agent 分工协作 → 交付一个结果。

让每一家公司都能用自然语言运行和管理自己的 Agent，同时确保数据不出域、执行过程可控制、结果可追溯。

## 愿景

OryxOS 希望成为 Agent 时代的运行底座。企业内的业务 Agent、跨团队协作 Agent，以及未来跨节点分布的 Agent，都可以在同一套底座上运行、被管理并协同工作。长期目标是进入 Apache 基金会并成长为 Apache 顶级项目。

OryxOS 是开源的 **Agent Harness OS**。Agent Harness 是套在模型外面、把模型变成能可靠做事的 Agent 的运行骨架，包括：

- 驱动 Reason → Act → Observe 的推理循环；
- 工具定义、调用和执行机制；
- 每次模型调用前的上下文组装；
- 会话记忆和长期记忆；
- 工具执行所需的沙箱、白名单和权限边界；
- 记录模型与工具行为的审计链路。

裸模型只会生成文本，Harness 才让模型能够可靠、安全地行动。

### 北极星公式

```text
自然语言 (md) + Memory + Tool + MCP (Connector)
              + Skill + 知识库 + Notify = 一个 Agent
```

一个目录定义一个 Agent，一个底座运行一群 Agent；私有部署，数据不出域。工具生态对接 MCP，Agent 协作面向 A2A，覆盖模型接入、推理循环、记忆、工具调用和对外服务五大核心能力。

> 北极星公式描述的是产品方向，不代表其中每项能力均已在当前版本完整交付。当前实现边界见“路线图”。

## 为什么需要 OryxOS

企业 Agent 从演示走向生产，通常会遇到四道门槛：

1. **定义 Agent 要写代码**：最懂业务的人反而无法直接定义 Agent。
2. **云平台要求数据离域**：隐私、合规和内部系统访问难以通过。
3. **执行过程是黑盒**：没有审计、白名单、隔离和人工审批，企业不敢让 Agent 执行真实动作。
4. **运行一个容易，运行一群困难**：缺少管理多个 Agent 生命周期、共享能力和协作关系的操作系统层。

OryxOS 的方向是用自然语言和 Markdown 降低定义门槛，通过私有部署保护数据，以沙箱、策略和审计控制执行，并为一群 Agent 提供统一运行底座。

更深一层的判断是：**生产级 Agent 的主要瓶颈通常不是模型本身，而是运行环境。** Agent 能否真正完成工作，取决于它能否取得正确上下文、使用受控工具、隔离并审计调用，以及在分布式协作中可靠传递消息。OryxOS 不是又一个 Agent，而是让许多 Agent 可靠运行和协同的底座。

## Agent runtime 与 Agent Harness OS

Agent runtime 让单个 Agent 跑起来，负责调用模型、执行工具、管理上下文和控制推理循环。

Agent Harness OS 位于 runtime 之上，管理一群 Agent，负责多个 Agent 的生命周期、统一的内外部接入、共享服务、多租户与治理，以及未来分布式形态下的跨节点协作。

| 层次 | 管理范围 | 主要职责 |
| --- | --- | --- |
| 模型 | 一次 LLM 调用 | 理解和生成 |
| Agent runtime / Harness | 一个 Agent | 推理循环、上下文、工具、记忆、沙箱、审计 |
| Agent Harness OS | 一群 Agent | 生命周期、共享能力、治理、通信和扩展 |

借操作系统类比，runtime 是单个进程的执行环境，Agent Harness OS 是管理一群进程、调度资源并提供共享服务的操作系统层。OryxOS 选择建设后者，同时从单节点 runtime 内核开始落地。

## 五大核心能力

### 1. 对接 LLM

通过 Provider 抽象统一接入主流模型。Agent 不感知具体厂商，可按显式名称映射选择 Provider，支持多个 Provider 并存，并为本地推理保留统一接口。

### 2. ReAct 循环

核心推理循环由 OryxOS 自己实现，不套用外部 Agent 框架。模型判断是否调用工具以及调用哪个工具；OryxOS 检查并执行调用，将观察结果回填给模型，直到产生最终响应或达到最大迭代次数。

### 3. 记忆

使用会话记忆和长期记忆两层结构，使 Agent 跨对话保留状态。长期记忆首先采用文件形态与关键词检索，并为后续向量检索升级预留接口。

### 4. 工具体系

Agent 通过工具操作外部世界。基础能力规划包含文件、Shell、HTTP 等工具，扩展方式按门槛分为三档：

1. 用 Agent 目录配置并复用现成 MCP Server；
2. 用任意语言编写自定义 MCP Server；
3. 使用原生 Java 方法实现深度集成。

### 5. 对外服务

通过 REST API 暴露运行能力，使任何开发语言和业务系统都能使用 HTTP 接入。

## 核心特性

- **一个目录 = 一个 Agent**：用包含 `AGENT.md` 的目录定义 Agent，减少业务 Agent 的代码开发。
- **Java 原生**：基于 Java 21，目标是单个可执行 JAR 部署，复用企业 Java 运维工具链。
- **私有可控**：部署在企业自己的 K8s、虚拟机或物理机，数据不出域，不锁定云厂商。
- **安全隔离**：将文件、命令和网络策略、强制沙箱、凭证管理及全链路审计作为架构基础。
- **自实现 ReAct**：直接掌控推理循环和工具调用决策。
- **开放标准**：工具对接 MCP，协作面向 A2A，Agent 目录借鉴开放 Skill 形态。
- **三档工具扩展**：从配置和现成 MCP，到自定义 MCP，再到原生 Java。
- **跨对话记忆**：会话记忆与长期记忆分层。
- **面向无状态扩展**：运行实例逐步无状态化、持久状态外置，为分布式演进准备边界。

## 路线图

开发原则是单机先行、克制聚焦：先把单节点运行时内核做扎实，再以真实使用数据推动分布式演进。

### 阶段一（当前）：单机运行时内核

- 当前仓库已经具备 Java 21、Maven 九模块、可执行 Boot JAR、可执行 CLI 和最小健康接口的工程骨架。
- 本阶段目标是跑通五大核心能力、配置即 Agent、多 Agent 并存、REST API 接入和 MCP 接入。
- 当前工程骨架不等同于完整的 Agent OS 产品，具体实现应以代码和进度文档为准。

### 阶段二（规划）：底座分布式

- 运行节点无状态化；
- 持久状态外置；
- 多副本部署、高可用和更大规模运行。

### 阶段三（愿景）：跨节点 Agent 协作

- 引入 Agent 通信底座并对接 A2A；
- 支持跨节点发现、委托和可靠异步协同；
- 实现“一句话发布任务，由一支 Agent 团队协作交付”的北极星体验。

### 横向能力

多租户、SSO、完整审计、工具策略、可观测和 Web 管理将在各阶段中逐步补齐。

## 设计原则

- **底座优先于 Agent**：最重要的交付不是某个特定 Agent，而是任意 Agent 都能可靠运行的环境。
- **自实现核心，可控优先**：直接实现推理循环，模型协议适配复用成熟组件。
- **配置即 Agent**：Agent 由配置和 Markdown 定义，而不是由业务代码写出。
- **对接开放标准**：工具用 MCP，协作用 A2A，技能采用开放格式。
- **无状态实例，状态外置**：为从单机平滑演进到分布式建立前提。
- **安全是地基，不是补丁**：最小权限、强制沙箱、凭证不落地和全链路审计从第一天进入架构。
- **分阶段克制**：当前聚焦运行时内核的最小完备集，每次升级都由真实需求证明必要性。
